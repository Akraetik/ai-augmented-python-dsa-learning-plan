## You've already done this

The read/write pattern from lesson 1.1 is two pointers moving the **same way**. `read` moves every step.
`write` moves only when something is kept. One fast, one slow.

This lesson uses the same shape on **two different sequences**.

## Is Subsequence

Lab 02: is `s` a subsequence of `t`? That means you can delete some characters from `t` (keeping the order)
and get `s`.

`"ace"` is a subsequence of `"abcde"`. `"aec"` is not: the order is wrong.

One pointer per string:

```
s = "ace"         t = "abcde"
     i                 j         'a' == 'a' → match. i moves. j moves.
      i                 j        'c' vs 'b' → no.    j moves.
      i                  j       'c' == 'c' → match. i moves. j moves.
       i                  j      'e' vs 'd' → no.    j moves.
       i                   j     'e' == 'e' → match. i moves.
i reached the end of s → True
```

- `j` (the pointer in `t`) moves **every** step. It's the fast one.
- `i` (the pointer in `s`) moves **only on a match**. It's the slow one.
- If `i` reaches `len(s)`, every character was matched in order. True.
- If `j` runs off the end first, False.

Why is it safe to match greedily, at the **first** place a character appears in `t`? Because matching
earlier never hurts. It leaves more of `t` for the remaining characters. That's a greedy argument, like lesson 1.4.

## Edge cases to check

- `s` is empty → always True. (The empty string is a subsequence of everything.)
- `t` is empty and `s` isn't → False.
- `s` longer than `t` → False. Your loop should handle this without a special case. Does it?

## Common mistake

Using `t.find(ch)` for each character of `s`, but searching from the start each time. That ignores order.
`"aec"` would wrongly pass. If you use `find`, pass the start position: `t.find(ch, j)`.

## Pattern trigger

> **"In order, but not necessarily next to each other" across two sequences → one pointer each; the slow one moves only on a match.**
