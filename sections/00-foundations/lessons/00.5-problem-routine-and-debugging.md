# 00.5 · The Problem Routine, Tracing, and Debugging

**Time:** 30 minutes. **Goal:** have a process to follow when you don't know what to do.

---

## Why a routine

When you're stuck, your brain wants to start typing. That's usually wrong.
Strong candidates spend the first third of their time **not coding**. They understand, plan, and pick a tool.
Then the code is short.

## The routine, with a real example

Problem: *Given a list of numbers, return the largest gap between two numbers that sit next to each other.*

### 1. Restate it

"I walk through neighbor pairs. For each pair I find the distance. I return the biggest distance."

Also answer: **what do I return?** One integer. (Mistake **M6** check.)

### 2. Work one example by hand

`[3, 9, 4, 4, 12]` → gaps are `6, 5, 0, 8` → answer `8`.

Writing it out shows you something: there are `len - 1` pairs, not `len`.

### 3. List edge cases

- One number: no pairs. What do we return? The problem must say. Say `0`.
- Two numbers: one pair.
- Negatives: `[-5, 5]` → gap is 10. Use `abs`.

### 4. Brute force, and its Big-O

Here, the simple way is already one pass: **O(n)**. Good. Often the brute force is O(n²) and step 5 improves it.

### 5. Pick the pattern

"Look at neighbors" → loop over indexes `0` to `len - 2`, read `nums[i]` and `nums[i + 1]`.

### 6. Code it

```python
def largest_gap(nums):
    best = 0
    for i in range(len(nums) - 1):          # stops so i + 1 stays in range (M5)
        gap = abs(nums[i + 1] - nums[i])
        if gap > best:
            best = gap                      # saved, not just computed (M4)
    return best                             # after the loop (M7)
```

### 7. Test it — by hand first

Trace `[3, 9, 4]`:

| i | nums[i] | nums[i+1] | gap | best |
|---|---|---|---|---|
| start | | | | 0 |
| 0 | 3 | 9 | 6 | 6 |
| 1 | 9 | 4 | 5 | 6 |

Returns 6. Correct. Now trace `[7]`: `range(0)` is empty. Returns 0. Correct.

Then scan for every mistake in MISTAKES.md. Then run the tests.

## How to trace code

Tracing means running the code in your head, on paper, one line at a time.
It's the single best way to find your own bugs, and interviewers expect it.

1. Make a table. One column per variable.
2. Step through each line. Update the table when a variable changes.
3. Use a **small** input. Two or three items.

Do it on paper at first. It's slower. That's the point.

## How to debug

When a test fails:

1. **Read the failure.** The lab shows input, expected, and what you got. Look at the difference.
2. **Make it small.** Find the smallest input that fails.
3. **Print the state.** Add one line inside the loop:
   ```python
   print(f"i={i} left={left} right={right} best={best}")
   ```
   Run it. Find the first line where the numbers go wrong.
4. **Explain the code out loud** to an empty chair. Line by line. You'll often hear the bug yourself.
   This is called rubber-duck debugging. It works.
5. **Check the mistake log.** Most bugs are repeat bugs.

Delete the debug prints before you submit.

## Reading error messages

| Error | Usual cause |
|---|---|
| `IndexError: list index out of range` | Off-by-one. You read `nums[len(nums)]` or `nums[i + 1]` at the end. |
| `KeyError: 'x'` | You read a dict key that isn't there. Use `.get(key, default)` or `in`. |
| `TypeError: 'NoneType' object is not ...` | Something returned `None`. Often `x = list.sort()`. |
| `TypeError: unhashable type: 'list'` | You put a list in a set or used it as a dict key. Use a tuple. |
| `UnboundLocalError` | You used a variable before setting it in that function. |
| Infinite loop (nothing happens) | A `while` loop never changes its condition. Look for a missing `+= 1`. |

## When you're really stuck

1. Solve a smaller version. Two items. One item.
2. Solve it slowly. Write the O(n²) version. A working slow answer beats nothing.
3. Ask: **what work am I repeating?** The fast version usually remembers something so it doesn't redo work.
4. Open Hint 1. Only Hint 1.
