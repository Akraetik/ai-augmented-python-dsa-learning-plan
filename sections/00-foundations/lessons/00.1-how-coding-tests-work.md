# 00.1 · How Coding Tests Work

**Time:** 20 minutes. **Goal:** know what you're being graded on before you practice.

---

## Two graders: correctness and speed

Every coding test grades two things.

1. **Correctness.** Does your function return the right answer for every input, including the strange ones?
2. **Performance.** Does it finish fast on huge inputs?

Most beginners only practice the first. Then they fail the second. Codility is blunt about this.
It shows you a "correctness" score and a "performance" score. A nested loop can get 100% on the first
and 0% on the second.

LeetCode does the same thing more quietly. It says **Time Limit Exceeded**.

So from day one, every lab in this course runs big inputs with a timer.

## What the code looks like

### LeetCode

LeetCode wraps your function in a class. You fill in one method.

```python
class Solution:
    def twoSum(self, nums: List[int], target: int) -> List[int]:
        # your code
        ...
```

Three things to notice.

- **`class Solution:`** is just a container. You don't need to understand classes to use it.
- **`self`** is the first parameter. Ignore it. Don't pass it. Don't use it (unless you write a helper method,
  then you call it as `self.helper(...)`).
- **`nums: List[int]`** is a *type hint*. It tells you `nums` is a list of integers. Python doesn't enforce it.
  It's documentation. Read it. It tells you what you're getting and what to return.

### Codility

Codility uses a plain function, usually named `solution`.

```python
def solution(A):
    # A is a list of integers
    ...
```

### This course

Labs use plain functions with type hints, like this:

```python
def two_sum(nums: List[int], target: int) -> List[int]:
    ...
```

To paste a lab answer into LeetCode, indent it under `class Solution:`, rename it to LeetCode's name,
and add `self` as the first parameter. That's it.

## Return, don't print

The grader calls your function and looks at what comes back. It does not read your screen.

```python
def add(a, b):
    print(a + b)     # WRONG: the grader gets None

def add(a, b):
    return a + b     # RIGHT
```

A function with no `return` gives back `None`. If a lab says every test returned `None`, this is why.

Some problems say **"modify the array in place, return nothing."** Then you change the list you were given,
and you don't return anything. The signature shows it: `-> None`.

> **Mistake M6:** not reading the return type. Before you plan, write `RETURNS: ___` at the top of your plan.

## Hidden tests

You see two or three examples. The grader runs dozens more. They test:

- **empty input** (`[]`, `""`)
- **one element**
- **all the same value**
- **negatives and zero**
- **the largest allowed input** (often 100,000 or more items)
- **already sorted, reverse sorted**

If your code only works on the examples, it doesn't work. Plan for the hidden tests.

## Constraints are a clue

Every problem lists constraints, like `1 <= nums.length <= 10^5`. That number tells you how fast you must be.
Lesson 00.2 shows you how to read it.

## The live interview is different

In a live round, a person watches you work. They grade:

| What | What it looks like |
|---|---|
| **Communication** | You say what you're thinking. You ask questions before coding. |
| **Problem solving** | You find a working approach, then improve it. |
| **Coding** | Clean, correct Python. Good names. |
| **Testing** | You trace your own code on an example and catch your own bugs. |

The best habit: **talk out loud while you practice.** Even alone. It feels silly. Do it anyway.
The Q&A session in each section trains this.

In 2026, big tech live rounds still turn AI off. Many companies also add a **debug-this-code** round:
they hand you broken code and watch you find the bug. Every section here has a Bug Hunt lab for that.

## Quick check

<details><summary>1. Your function prints the right answer but the grader says it's wrong. Why?</summary>

You printed instead of returning. The grader got `None`.
</details>

<details><summary>2. What do you do with `self` in a LeetCode solution?</summary>

Leave it as the first parameter and otherwise ignore it. Don't pass it when you test.
</details>

<details><summary>3. Your code passes every example but fails "performance." What does that usually mean?</summary>

It's correct but too slow on big inputs, often because of a loop inside a loop. Lesson 00.2 covers this.
</details>
