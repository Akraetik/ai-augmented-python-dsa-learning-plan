## Flip the question

Lesson 3.2 wanted the **longest** window that stays valid. Now you want the **shortest** window that
becomes valid.

- the shortest subarray with sum at least `target`
- the shortest substring that contains every letter of `t`

Same two pointers. One change in **where you record.**

## The template

```python
left = 0
best = float("inf")
for right in range(len(nums)):
    # 1. GROW: add nums[right]
    while WINDOW_IS_VALID:
        # 2. RECORD: this window works. Is it the shortest so far?
        best = min(best, right - left + 1)
        # 3. SHRINK: try to make it shorter
        # remove nums[left]
        left += 1
return best if best != float("inf") else 0
```

Compare the two side by side:

| | Longest valid (3.2) | Shortest valid (3.3) |
|---|---|---|
| `while` runs when the window is... | **broken** | **valid** |
| You record... | **after** the `while` | **inside** the `while` |
| `best` starts at... | 0 | infinity |

Say it out loud: *longest — shrink while broken, record after. Shortest — record while valid, then shrink.*

## Minimum Size Subarray Sum (lab 06)

All numbers are **positive**. Find the shortest run with sum at least `target`. Return 0 if none exists.

```
nums = [2, 3, 1, 2, 4, 3], target = 7

right  window             sum   valid?   action
  3    [2 3 1 2]           8     yes     record 4, drop 2 → [3 1 2] sum 6, stop
  4    [3 1 2 4]          10     yes     record 4, drop 3 → [1 2 4] sum 7
                                  yes     record 3, drop 1 → [2 4] sum 6, stop

```

Don't forget the "none exists" case. If `best` is still infinity, return 0. (Mistake **M6**: read what it

## When sliding windows break: negative numbers

Lab 06 says all numbers are positive. That's not decoration. It's what makes the window work.

With only positive numbers:
- growing the window always **raises** the sum,
- shrinking it always **lowers** the sum.

So "too small → grow, big enough → shrink" always moves you toward the answer.

With negatives, that breaks. `[2, -1, 2]`, target 3. The whole list sums to 3. But shrinking from the left
drops the 2 and the sum goes to 1. Dropping the −1 next would *raise* it. The window can't tell which way
to move.

When a problem has negatives and asks about subarray sums, sliding window is the wrong tool. You'll use
**prefix sums with a hashmap** instead (Section 05). Knowing *when not* to use a pattern is part of the skill.

## Minimum Window Substring (lab 07, Stretch)

Find the shortest substring of `s` that contains every letter of `t`, **counting repeats**.
`s = "ADOBECODEBANC"`, `t = "ABC"` → `"BANC"`.

Valid means: for every letter in `t`, the window has at least as many of it.

Checking all of `t`'s letters every step works, but there's a neat counter:

- `need` = Counter of `t`. `required` = how many **different** letters `t` has.
- `have` = how many different letters are currently satisfied (window count ≥ need count).

When a letter enters and its window count **reaches exactly** what `t` needs, `have += 1`.
When a letter leaves and its window count **drops below** what `t` needs, `have -= 1`.
The window is valid when `have == required`.

The rest is the shortest-valid template. Record the window's **start and length** (not just the length),
because you return the substring itself.

Trace `s = "XAYBZACB"`, `t = "ABC"` on paper before you code. The answer is `"ACB"`.

## Pattern trigger

> **"Shortest / minimum window that satisfies X" → grow right; while valid, record then shrink left. Only safe if growing and shrinking move the condition one way (no negatives in sums).**
